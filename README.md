# TunnelVPN

Два туннеля WireGuard одновременно: рабочий и личный. Подсети рабочего конфига
идут в один туннель, всё остальное — в другой. Под капотом
[sing-box](https://sing-box.sagernet.org) (форк [sing-box-lx](https://github.com/Leadaxe/sing-box-lx) с поддержкой AmneziaWG).

Приложение для Windows: служба держит туннель и правит маршруты, значок в
трее — включает и выключает (правый клик — меню, двойной левый — окно), окно
показывает состояние, конфиги и живой лог.

> **Статус: бета, обкатано на Windows 11.** Оба туннеля поднимаются разом,
> рабочая сеть и личный выход работают, трей управляет службой. Установщик
> и портативная версия пока проверены только сборкой.

## Как разводится трафик

Правила проверяются по порядку, до первого совпадения:

1. адрес в подсетях конфига туннеля «по списку» (`AllowedIPs`) или запись из его
   `include` (домен — по SNI/Host) → этот туннель, кроме записей его `exclude`
2. адрес локальный (`10/8`, `172.16/12`, `192.168/16`) → мимо туннелей
3. остальное → личный туннель

Домены из `include` резолвит DNS этого туннеля через правила sing-box —
запросы идут прямо через tun, отдельная настройка системы не нужна.

## Устройство

```
lib/tunnelvpn/
  paths.py          где что лежит: код, данные, бинарники
  winnet.py         маршруты, интерфейсы, IPv6, DNS — через PowerShell
  buildconfig.py    .conf → config.json для sing-box
  tunnel.py         подъём/остановка, журнал владения маршрутами, откат
  probe.py          пробер состояния: что поднято, есть ли утечка
  ipc.py            именованный канал между службой и треем
  service.py        служба Windows: сводит всё вместе
  portable.py       версия без установки: то же ядро, но в своём процессе
  tray.py           значок в трее
  window.py         окно на WebView2, мост к вёрстке
  cli.py            консольное управление (tunnelvpn start/stop/status/...)
  ui/index.html     вёрстка окна
installer/
  tunnelvpn.spec    PyInstaller: два exe, одна общая папка
  tunnelvpn.iss     Inno Setup: служба, права на данные, ярлыки
  build.ps1         сборка целиком, от окружения до установщика
conf/               tunnels.json и .conf-файлы туннелей, вне гита
```

Туннель правит таблицу маршрутов, поэтому им владеет служба под LocalSystem,
а трей и окно шлют ей команды через именованный канал. Трей запускается от
администратора: конфиги с приватными ключами меняются только с правами, и
иначе UAC спрашивал бы на каждое добавление. Окно открывается из трея и
наследует его права.

**Чужое не трогаем.** Половинки дефолтного маршрута (`0.0.0.0/1`,
`128.0.0.0/1`) — общий ресурс: ровно их же ставят себе Amnezia, официальный
клиент WireGuard и любой другой VPN. Каждое снятие маршрута сначала проверяет
владельца по журналу и по факту, что интерфейс — наш, и только потом снимает
строку.

## Как запускать

Три способа, от простого к полному.

**Портативно — один файл.** `TunnelVPN-Portable.exe`: ни установки, ни службы.
Двойной клик, один раз UAC — и значок в трее. Внутри уже всё, включая sing-box
и wintun. Конфиги и состояние кладутся в `TunnelVPN-Data\` рядом с exe, так что
папку можно унести целиком.

Отличие одно: туннель держит сам процесс, а не служба. «Закрыть»
в трее в обеих версиях опускает туннель, возвращает маршруты и закрывает
значок.

**Установка.** `TunnelVPN-<версия>-setup.exe` ставит службу, ярлыки и автозапуск.
Служба переживает выход из системы и перезагрузку. Трей при входе в систему
поднимает задача планировщика «TunnelVPN Tray» с наивысшими правами — без
UAC. Ярлык при живом трее только открывает окно, а без трея запускает ту же
задачу; UAC спросит, только если автозапуск при установке сняли.

**Из исходников** — для разработки, см. ниже.

Готовых `.exe` в репозитории нет: их собирает `installer\build.ps1` на
Windows-машине (раздел «Сборка»).

## Из исходников

Нужны Windows 10/11, Python 3.14 (на нём собираются релизы:
`winget install Python.Python.3.14`), права администратора и два бинарника рядом
в `lib/bin\`:

* [`sing-box-lx`](https://github.com/Leadaxe/sing-box-lx/releases) —
  `sing-box-<версия>-windows-amd64.zip`, форк с AmneziaWG;
* `wintun.dll` — [wintun.net](https://www.wintun.net/), тот же файл, что несёт
  официальный клиент WireGuard.

```powershell
git clone https://github.com/enkeym/dual-vpn.git
cd dual-vpn

py -3.14 -m venv lib\venv
lib\venv\Scripts\pip install -r requirements.txt

copy \путь\к\personal.conf conf\
copy \путь\к\wg0-corp.conf conf\

set TUNNELVPN_DATA=%cd%
lib\venv\Scripts\python -m tunnelvpn.cli service console
```

`service console` запускает логику службы прямо в консоли, без установки —
удобно для разработки: трей (`python -m tunnelvpn.cli tray`) и окно подключатся
к ней так же, как к настоящей службе.

## Сборка установщика

```powershell
powershell -ExecutionPolicy Bypass -File installer\build.ps1
```

Скрипт сам создаёт окружение на Python 3.14 (окружение на другой версии
пересоздаёт), ставит закреплённые зависимости, рисует значок и собирает:

* `dist\TunnelVPN-Portable.exe` — портативная версия, один файл;
* `dist\TunnelVPN\` — установочная пара `TunnelVPN-Tray.exe` (трей) и `tunnelvpn.exe`
  (CLI и служба);
* `installer\Output\TunnelVPN-<версия>-setup.exe` — если найден
  [Inno Setup](https://jrsoftware.org/isdl.php). Без него сборка
  останавливается на готовых exe.

Установщик заводит `C:\ProgramData\TunnelVPN` с раздельными правами (`conf\` —
только SYSTEM и администраторы, там приватные ключи; `state\` — пользователям
на чтение, оттуда трей берёт состояние; кроме `state\run\` с собранными
конфигами sing-box — он закрыт, как `conf\`), ставит службу на автозапуск и вешает
ей перезапуск при падении. Удаление снимает туннель, службу и задачу
автозапуска и спрашивает, удалять ли конфиги с ключами (по умолчанию — нет).

Прежнюю установку под именем DualVPN установщик видит как свою прошлую
версию: снимает её службу, задачу и ярлыки и переносит `C:\ProgramData\DualVPN`
в `C:\ProgramData\TunnelVPN` вместе с конфигами и ключами. Портативная версия
так же подхватывает `DualVPN-Data\` рядом с exe.

## Конфиги

Туннели описаны в `conf\tunnels.json`, конфиги каждого лежат в его папке
`conf\tunnels\<id>\`. Правила принадлежат туннелю, а не файлу: заменили `.conf` —
правила остались. Проще всего править в окне; файл выглядит так:

```json
{"version": 1, "log_level": "info",
 "tunnels": [
   {"id": "work", "name": "Работа", "mode": "list", "active": "corp",
    "enabled": true,
    "include": ["corp.example"], "exclude": ["198.51.100.7/32"]},
   {"id": "home", "name": "Личный", "mode": "all", "active": "nl-1",
    "enabled": true, "include": [], "exclude": []}]}
```

| поле | что задаёт |
|---|---|
| `id` | имя папки конфигов: латиница в нижнем регистре, цифры, дефис |
| `mode` | `list` — в туннель идёт только `include` и `AllowedIPs` его конфига; `all` — весь остальной трафик, такой туннель (основной) не больше одного |
| `active` | активный конфиг из папки туннеля, без `.conf`; у основного — это профиль (`tunnelvpn profile <имя>`). Конфиг один — можно не указывать |
| `enabled` | `false` выключает туннель «по списку», не теряя конфигов и правил (`tunnelvpn enable\|disable`); основной всегда включён |
| `include` | что ещё пускать через туннель: адреса, подсети, домены (со всеми поддоменами; `*.домен` — только поддомены). Домены резолвит DNS туннеля, первый домен без `*.` — ещё и проверка связи |
| `exclude` | что не пускать, даже если попадает в `include` или подсети `AllowedIPs` |
| `log_level` | подробность журналов sing-box в `state/logs/`: по умолчанию `info`; `debug` — пока ищем причину сбоя, журнал растёт в разы. Выше `info` (`warn`, `error`) перестаёт пополняться `state/paths.json` — сколько соединений к какому адресу ушло через каждый туннель |

У туннеля «по списку» в конфиге не должно быть `AllowedIPs = 0.0.0.0/0`: подсети берутся
оттуда, и он заберёт весь трафик. Старый `conf\site.env` служба один раз переносит
в `tunnels.json` (`CORP_DOMAINS` → `include`, `SB_CORP_EXCLUDE` → `exclude`, `SB_LOG_LEVEL` →
`log_level`) и оставляет рядом как `site.env.bak`.

Проще всего добавлять через трей (пункт туннеля: «Работа: добавить конфиг…»
или имя его конфига) или через окно, и при поднятом VPN тоже: перезапускается
только процесс этого туннеля, tun и интернет не падают. Так же на лету —
списки и подсети туннелей, включение и выключение туннеля «по списку» и смена
основного (в том числе «Всё остальное напрямую»). VPN выключается и включается
целиком, только если сменилось то, что держит основной процесс: новый туннель,
адрес DNS туннеля «по списку», MTU основного, — или sing-box не принял новые
правила (причина — в журнале службы). Имя файла
может быть любым: конфиг ложится под ним, недопустимые знаки становятся `_`.

* из трея конфиг ложится в папку своего туннеля и сразу становится активным,
  прежние остаются; если у него тот же частный DNS, что у выбранного конфига
  туннеля «по списку», — это новый доступ в ту же сеть, и он заменяет прежний
  (правила туннеля остаются);
* «Добавить конфиг…» в окне выбирает место по `AllowedIPs`: с `0.0.0.0/0` —
  запасным в основной туннель (нет основного — он появляется); тот же частный
  DNS, что у туннеля «по списку», — вместо его конфига; подсети пересекаются,
  а DNS другой — окно спрашивает, заменить или завести отдельный туннель;
  иначе — новый туннель «по списку»;
* файл без `[Interface]` и `[Peer]` не принимается — так случайно выбранный
  `site.env` не ляжет вместо ключей; так же и конфиг, из которого не собрать
  туннель: без `PrivateKey`, `PublicKey`, `Endpoint` или `AllowedIPs`,
  `Endpoint` не в виде `host:port`, опечатка в числе (`MTU`, поля AmneziaWG).
  Окно показывает причину, а VPN продолжает включаться с прежними конфигами.

## Из консоли

```
tunnelvpn status              что сейчас поднято
tunnelvpn start [ПРОФИЛЬ]     поднять
tunnelvpn stop                опустить и откатить маршруты
tunnelvpn list                туннели и их конфиги (* — активный)
tunnelvpn use ТУННЕЛЬ КОНФИГ  выбрать конфиг туннеля (туннель — id или имя)
tunnelvpn profile ИМЯ         выбрать конфиг основного туннеля
tunnelvpn enable ТУННЕЛЬ      включить туннель «по списку» (disable — выключить)
tunnelvpn log [N]             последние строки журнала sing-box
tunnelvpn version

tunnelvpn service install     поставить и запустить службу (от администратора)
tunnelvpn service remove
tunnelvpn service start|stop|restart
```

## Особенности

**MTU.** Если в конфиге нет строки `MTU`, подставляется 1280. С 1420 часть
серверов завершает рукопожатие, но не пропускает данные — туннель выглядит
поднятым, а интернета нет. У AmneziaWG с junk-параметрами (ненулевые `Jc`,
`S1`–`S4`) MTU больше 1280 при сборке снижается до 1280: удлинённые пакеты
иначе не проходят в мобильных сетях и вложенных туннелях. Файл конфига не меняется.

**Сон.** Пока туннель поднят, служба держит `SetThreadExecutionState`, чтобы
система не засыпала по простою. После сна открытые до него соединения мертвы —
восстановление туннеля их не воскрешает.

**IPv6.** Личный сервер v6-адрес не выдаёт, нести v6 в туннель нечем.
На время работы туннеля исходящий IPv6 блокируется правилом брандмауэра и
снимается при выключении — обратимо и мгновенно, в отличие от отключения
адаптера.

**Утечка.** Перед подъёмом туннеля запоминается адрес провайдера, утечкой
считается совпадение с ним. Сравнивать с адресом сервера ненадёжно: он может
выходить не тем адресом, на котором принимает соединения.

## Тесты

```bash
pip install pytest
python -m pytest tests -q
```

Гоняются в CI на каждый push. Покрывают чистую логику: разбор `.conf`,
границы прав на канале, чтение и запись `tunnels.json` и — главное — владение
маршрутами: половинки дефолта общие с другими VPN-клиентами, и ошибка там
означает оторванную сеть у соседнего туннеля, а не своё «не работает».

Чего они не проверяют: поведение самой Windows — именованные каналы,
PowerShell, службы, wintun, сборку PyInstaller. Всё это живёт только на
настоящей машине, и найденные до сих пор ошибки были именно там.
