# DualVPN

Два туннеля WireGuard одновременно: рабочий и личный. Подсети рабочего конфига
идут в один туннель, всё остальное — в другой. Под капотом
[sing-box](https://sing-box.sagernet.org).

Приложение для macOS: значок в меню-баре и окно с состоянием, конфигами и
живым логом.

## Как разводится трафик

Правила проверяются по порядку, до первого совпадения:

1. адрес в подсетях рабочего конфига (`AllowedIPs`) → рабочий туннель
2. адрес локальный (`10/8`, `192.168/16`) → мимо туннелей
3. остальное → личный туннель

Домены рабочей сети резолвит корпоративный DNS через `/etc/resolver`,
остальные — публичный через личный туннель.

## Установка

Скачай `.dmg` из [релизов](https://github.com/sotakeiteasy/dual-vpn/releases)
(«DualVPN macOS X.Y.Z»; там же лежат и Windows-релизы, у них теги `v*`),
перетащи в «Программы». Приложение не подписано, поэтому первый запуск —
правой кнопкой → «Открыть».

Дальше в окне: «Установить службу…» (спросит пароль), «Добавить конфиг…»,
«Настроить рабочую сеть…», «Включить».

Всё, включая sing-box, лежит внутри `.app`. Конфиги и состояние —
в `~/Library/Application Support/DualVPN`.

Обновление — из окна. Приложение раз в 6 часов смотрит релизы macOS, и
если вышла новая версия, в подвале окна появляется «есть X.Y.Z — Обновить».
Кнопка скачивает образ, сверяет его sha256, спрашивает пароль и заменяет
приложение. Служба переставляется вместе с ним: права на управление ею у новой
версии могут быть другими. Поднятый туннель после этого поднимается снова,
а приложение перезапускается уже новой версией.

Вручную — как при установке: перетащи новый `.app` поверх старого и нажми
«Установить службу…» ещё раз.

### Переход с установки из исходников

Если ставил через `install.sh`, служба работает из папки проекта, а
«Обновить» меняет только приложение. Чтобы перевести на релиз и службу:

1. Выключи VPN.
2. Перетащи `DualVPN.app` из `.dmg` в «Программы» с заменой (Finder спросит
   пароль: старое приложение ставилось от root).
3. Переставь службу из приложения:

   ```bash
   sudo bash /Applications/DualVPN.app/Contents/Resources/install-daemon.sh
   ```

   Конфиги (`conf/*.conf`, `conf/site.env`) и выбранный профиль скопируются
   из проекта в `~/Library/Application Support/DualVPN`, если там их ещё
   нет. Папку проекта установщик не трогает — её можно удалить сам.
4. Перезапусти приложение: каталог данных оно читает при старте.

## Из исходников

Нужен macOS 13+, Python 3.9+ и бинарник
[sing-box-lx](https://github.com/Leadaxe/sing-box-lx) — форк с AmneziaWG (2.0 и 3.x — нужен lx.32 или новее),
в основной сборке его нет.

```bash
git clone git@github.com:sotakeiteasy/dual-vpn.git && cd dual-vpn

VER=1.14.1-lx.12; ARCH=darwin-arm64
mkdir -p lib/bin && cd lib/bin
curl -LO https://github.com/Leadaxe/sing-box-lx/releases/download/v$VER/sing-box-$VER-$ARCH.tar.gz
tar xzf sing-box-$VER-$ARCH.tar.gz --strip-components=1 sing-box-$VER-$ARCH/sing-box
chmod +x sing-box && xattr -dr com.apple.quarantine sing-box && cd ../..

cp ~/mine/personal.conf ~/mine/wg0-corp.conf conf/
bash install.sh                    # без sudo, пароль спросит сам
```

`install.sh` создаёт окружение, собирает `.app`, прогоняет проверки и только
потом трогает систему. Он же и обновление: `git pull && bash install.sh`.

Конфиги, `site.env`, бинарник и `lib/state/` вне гита и переустановку
переживают.

## Конфиги

Тип определяется именем файла:

| | имена | формат |
|---|---|---|
| рабочий | `corp.conf`, `wg.conf`, `wg-*.conf`, `wg0-*.conf` | WireGuard |
| личный | `personal.conf`, `awg-*.conf`, `amnezia-*.conf` | WireGuard или AmneziaWG |

Рабочий должен быть ровно один, личных сколько угодно — переключаются в окне.
У рабочего не должно быть `AllowedIPs = 0.0.0.0/0`: маршруты берутся оттуда,
и он заберёт весь трафик. Образцы — в `conf/*.example`.

Домены рабочей сети задаются в окне или в `conf/site.env`
(см. `site.env.example`).

## Из терминала

```bash
sudo ./vpn ui        # панель вместо приложения
sudo ./vpn start     # поднять
sudo ./vpn stop      # опустить и откатить маршруты
sudo ./vpn status
sudo ./vpn diag
./vpn list           # какие конфиги видны
./vpn version
```

## Устройство

```
vpn                     сборка конфига, маршруты, откат
lib/scripts/
  build-config.py       .conf → config.json
  menubar.py            значок в меню-баре
  menumodel.py          что показать в меню в каждом состоянии
  control.py            включение/выключение/перезапуск: по одной, до результата
  window.py             окно на WKWebView
  ui/index.html         вёрстка окна
  ui/view.js            что показать в окне в каждом состоянии
  tui.py                панель в терминале, общий пробер состояния
  selftest.sh           проверки
  make-dmg.sh           сборка образа для релиза
  release.sh            выпуск: VERSION, тег mac-v*, пуш
  changelog.sh          раздел версии из CHANGELOG.md
lib/launchd/            описание службы
tests/                  тесты: python -m unittest, node --test
windows/                вариант для Windows, со своим README
```

Туннель правит таблицу маршрутов, поэтому им владеет служба launchd, а
приложение работает от обычного пользователя и шлёт ей две команды. Права
выданы точечно, через `/etc/sudoers.d`.

Кнопки не шлют команды напрямую: операцию ведёт `control.py` — в фоне, по
одной за раз, и ждёт настоящего результата. Перезапуск — это полное
выключение (служба вышла, маршруты сняты) и затем включение. Если старт не
удался, служба пишет причину в `lib/state/last-error`; окно показывает эту
причину и хвост лога.

Сама служба не стартует ни при загрузке, ни после падения: в её plist нет
`KeepAlive`, потому что по `man launchd.plist` он подразумевает `RunAtLoad`.
Упавший в работе туннель поднимается кнопкой.

## Особенности

**MTU.** Если в конфиге нет строки `MTU`, подставляется 1280. С 1420 часть
серверов завершает рукопожатие, но не пропускает данные — туннель выглядит
поднятым, а интернета нет.

**Сон.** Пока туннель поднят, система не засыпает по простою (`caffeinate -i`);
закрытие крышки этим не покрывается. После сна открытые до него соединения
мертвы — восстановление туннеля их не воскрешает.

**Утечка.** Перед подъёмом туннеля запоминается адрес провайдера, утечкой
считается совпадение с ним. Сравнивать с адресом сервера ненадёжно: он может
выходить не тем адресом, на котором принимает соединения.

## Проверки

```bash
bash lib/scripts/selftest.sh                     # всё сразу
lib/venv/bin/python -m unittest discover -s tests  # только тесты
node --test tests/test_view.js                   # логика окна
```

Синтаксис, кодировки, ротация логов, plist, тесты из `tests/` (кнопки и
таймауты на поддельной службе, меню, сборка AWG 2/3-конфигов с проверкой
самим sing-box, запись причины отказа), а для собранного приложения —
подпись, запуск, исключения в JS и то, что каждая часть окна отработала.
`install.sh` прогоняет их сам и при провале ничего не ставит.

## Выпуск

```bash
bash lib/scripts/release.sh 0.1.4
```

Сначала в `CHANGELOG.md` нужен раздел `## 0.1.4`: что нового, словами
человека. Он станет описанием релиза, без него скрипт версию не выпустит.

Скрипт проверяет, что дерево чистое и `main` совпадает с `origin/main`,
гоняет тесты, пишет номер в `VERSION`, коммитит «Выпуск macOS 0.1.4», ставит
тег `mac-v0.1.4` и пушит. Дальше GitHub Actions (`.github/workflows/mac.yml`)
на macOS-раннере качает sing-box, собирает `.app`, прогоняет `selftest.sh`
и выкладывает релиз «DualVPN macOS 0.1.4» с `DualVPN-0.1.4.dmg` и `.sha256`.
Тег с номером, отличным от `VERSION`, сборку роняет.

Теги macOS — `mac-v*`, у Windows-версии — `v*` в ветке `windows`; сборки друг
друга не задевают. Образ без релиза — «Run workflow» у workflow macOS, он
появится артефактом прогона. Локально тот же образ: `bash lib/scripts/make-dmg.sh`.

## Удаление

Из исходников — `bash install.sh remove`. Установленное из `.dmg`: перетащи
`.app` в корзину, затем

```bash
sudo launchctl bootout system/local.singbox-lx
sudo rm /Library/LaunchDaemons/local.singbox-lx.plist /etc/sudoers.d/singbox-lx
```

Конфиги при этом остаются: `~/Library/Application Support/DualVPN`.
